# 性能の記録

M1 の手順 D-16（性能スパイク）で、基準の PC で描画の速さを測った結果です。
設計を変えたときや、M1 の仕上げ（手順 I-39）で測り直して、ここに追記します。

## 測り方

```bash
nmm bench --video <1080p の H.264 動画> --frames 120 --workers 3
```

- `nmm bench` は、作業フォルダ（省略すると一時フォルダの `nmm-bench`）に素材の画像を作り、1080p・30fps・8 レイヤーのシーンを描いて測ります。
- シーンの中身は次のとおりです。
  - 背景（1920×1080）
  - 動画（1080p の H.264 を 0.6 倍で表示）
  - 大きな写真（4000×3000 を 0.25 倍で表示）
  - 動く透過画像（800×600）
  - 図形
  - 字幕（影付き）
  - タイトル（縁取り付き、回転するアニメーション）
  - 立ち絵の代わりの透過画像
- エフェクトありの場面では、3 つのレイヤーにぼかしと色調補正をかけます。
- 最初の 3 枚は準備（キャッシュの作成、デコーダーを開く、フォントの読み込み）なので、計測に含めません。
- 「スレッド 3」は、3 つのスレッドが別々のフレームを描いたときの、1 秒あたりの枚数（スループット）です。
- `--only` で、測る場面を選べます（`full`・`half`・`half-effects`・`full-effects`・`seek`）。
- ノート PC なので、続けて測ると温度で 2〜3 割ほど遅くなることがあります。比べるときは、間を空けて何回か測ります。

## 2026-11-03（D-16）

環境は、Panasonic Let's note SV1（CF-SV1）です。Core i5-1145G7（4 コア 8 スレッド）、Iris Xe、メモリ 16GB、Windows 11 Pro で、電源につないだ状態・電源プランは「バランス」です。
動画は `testsrc2` で作った 1080p30 の H.264（CRF 20、キーフレームは 2 秒ごと、B フレーム 2 枚）です。

| 場面 | スレッド | 平均（ms） | 95%（ms） | fps |
| --- | ---: | ---: | ---: | ---: |
| フル解像度・8 レイヤー（動画あり） | 1 | 31.6 | 52.9 | 31.6 |
| フル解像度・8 レイヤー（動画あり） | 3 | 55.5 | 84.0 | 53.6 |
| 1/2 解像度・8 レイヤー（動画あり） | 1 | 14.7 | 20.6 | 67.9 |
| 1/2 解像度・8 レイヤー（動画あり） | 3 | 23.1 | 32.1 | 129.0 |
| 1/2 解像度・3 レイヤーにぼかしと色調補正 | 1 | 29.7 | 46.2 | 33.7 |
| 1/2 解像度・3 レイヤーにぼかしと色調補正 | 3 | 36.6 | 53.7 | 81.7 |
| フル解像度・3 レイヤーにぼかしと色調補正 | 1 | 60.3 | 83.8 | 16.6 |
| フル解像度・3 レイヤーにぼかしと色調補正 | 3 | 87.7 | 122.7 | 33.8 |
| フル解像度・8 レイヤー（動画なし） | 1 | 13.9 | 17.3 | 71.9 |

止まっているときに、ばらばらの位置を表示する時間（1/2 解像度）は、画像だけなら 4.3ms、動画ありなら 95ms でした。

### 目標との比較

| 目標 | 結果 |
| --- | --- |
| 1/2 解像度のプレビューで 30fps | 1 スレッドでも 68fps |
| フル解像度・8 レイヤーで 30fps（動画ありは 24fps 以上） | 1 スレッドで平均 32fps（95% は 53ms）、3 スレッドで 54fps |
| 1/2 解像度で、3 レイヤーにぼかしと色調補正をかけて 30fps | 1 スレッドで 34fps、3 スレッドで 82fps |
| 止まっているときのシーク（画像のみ 50ms・動画 200ms 以下） | 4.3ms・95ms |

すべての目標に届いたので、設計（CPU 描画で、別々のフレームを並列に描く）は変えません。GPU 描画の前倒しも不要です。
ただし、フル解像度は 1 スレッドだと 95% が 1 フレームの時間（33ms）を超えます。そのため、FrameScheduler（D-17）で 2〜3 スレッドの並列描画と先読みを使う前提です。

### 測っている間に見つけて直したこと

| 問題 | 対策 |
| --- | --- |
| 動画の RGB への変換（swscale の `ACCURATE_RND`・`FULL_CHR_H_INT`）が、1080p で 1 フレームあたり約 7ms かかっていた | `ConversionQuality` を加えた。プレビューは速さ優先（`Fast`）、書き出しは質優先（`Accurate`、既定）。ハードウェアデコードの 1 フレームは 13.3ms → 6.7ms、シークは 160ms → 90ms になった |
| 3 スレッドで描くと 7.9fps まで落ちた。スレッドごとにフレームの順番が前後し、動画のデコーダーが毎回キーフレームまで戻っていた | ほぼ順番どおりに求められているときは、目的のフレームの手前 8 フレームも覚えるようにした（54fps に回復） |
| 前へのシークで、目的のフレームより前の、どこからも参照されないフレーム（B フレーム）もデコードしていた | 目的の 4 フレーム手前までは、デコーダーに飛ばさせる（`skip_frame`）。シークが 1〜2 割速くなった |

### わかったこと（後の手順への引き継ぎ）

- **動画のデコード**：このプレビューの大きさでは、ソフトウェアデコード（1 フレーム約 4ms）のほうが、ハードウェアデコード（約 6ms）より速いです。ハードウェアデコードは、GPU からメインメモリへの転送に時間がかかっています。
  - CPU の負荷と発熱を下げるため、既定はハードウェアデコードのままにします。
  - コピーをなくす仕組みは、M2 で入れます。
- **D-17（FrameScheduler）**：動画のフレームは、デコーダーごとに順番に求めるようにします（並列に描くのは合成だけ）。あわせて、少し先のフレームを先に描いておきます。
- **エフェクト**：フル解像度で 3 レイヤーにかけると、1 フレームあたり約 45ms 増えます。色調補正（C# で 1 画素ずつ計算）とぼかしが大きいので、M2 の GPU シェーダーの最初の対象にします。

## 2026-11-04（I-39：M1 の仕上げ）

環境は D-16 と同じです（Let's note SV1、電源につないだ状態）。サンプルプロジェクト（`samples/`）を使い、`nmm bench --project` で測りました。

```bash
nmm bench --project samples/general/general.nmmproj --only playback-half
nmm bench --project samples/general/general.nmmproj --only export --repeat 60
```

- 再生は、音を出さない仮のデバイスの時計で最後まで再生し、画面の更新の間隔（16ms）でフレームを取り出して、間に合わなかったフレームを数えます。
- 書き出しは、10 秒のシーンを 60 回つなげた 10 分の動画を、プリセット「シーンの大きさのまま」（H.264・12Mbps）で書き出します。
- 測る場面ごとに、別のプロセスで測っています（同じプロセスで続けて測ると、前の場面のメモリが残るため）。

| 目標 | 結果 | 判定 |
| --- | --- | --- |
| サンプルを 1/2 解像度でプレビュー：30fps、ドロップ 1% 以下 | 一般：0〜0.4%、ゆっくり：0% | 達成 |
| フル解像度・8 レイヤー（＋1080p H.264 動画）：30fps（動画ありは 24fps 以上） | D-16 のとおり（3 スレッドで 54fps）。サンプルのフル解像度の再生は 0.4% | 達成 |
| 1/2 解像度で、ぼかしと色調補正を 3 レイヤー：30fps | D-16 のとおり（3 スレッドで 82fps） | 達成 |
| 止まっているときのシーク（画像のみ 50ms・動画 200ms 以下） | D-16 のとおり（4.3ms・95ms） | 達成 |
| 10 分の動画の書き出し（QSV）：実時間の 2 倍速（最低でも等速） | h264_qsv で 301.7 秒、実時間の 1.99 倍 | ほぼ達成（最低の条件は達成） |
| セリフ 1 行の生成から試聴まで：100ms 以下 | SAPI で 1 回目 147ms（エンジンの準備を含む）、2 回目から平均 38ms | 2 回目から達成 |
| 録音の停止からタイムラインに表示されるまで：300ms 以下 | 3 秒の録音で 50ms | 達成 |
| アイテム 3,000 個のタイムライン：スクロール 60fps | 画面のない環境の CPU 描画で、1 回 19ms（約 53fps） | 未達（下に説明） |
| 起動時間 3 秒以下・メモリ 2.5GB 以下 | 起動 2.4〜2.6 秒（PC を起動して最初の 1 回は 3.9 秒）。メモリは起動後 300MB、再生中の最大 1.35GB（フル解像度）・0.85GB（1/2） | 起動は 2 回目から達成、メモリは達成 |

### 調整したこと

| 問題 | 対策 |
| --- | --- |
| 一般のサンプルの 1/2 解像度の再生で、2.6% のフレームが間に合わなかった。止まっている背景の色調補正や、動く文字の発光を、毎フレーム計算し直していた | エフェクトはローカル座標でかけるので、素材・エフェクトの値・細かさが同じなら結果を使い回すようにした（SkiaCpuBackend の EffectResultCache、128MB）。ドロップは 0〜0.4% になった |
| フル解像度の再生で、メモリが 2.5GB 近くまで増えた | 描いたフレームを覚えておく量を 1GB から 512MB にし、使わなくなったメモリを早めに返す設定（`System.GC.ConserveMemory`）にした。最大 2.05GB → 1.35GB |
| アイテム 3,000 個のタイムラインの描画が 1 回 30ms かかっていた | 色のブラシと、アイテムの名前などの文字の配置を使い回すようにした（19ms） |
| 起動が 3〜4 秒かかっていた | 起動時に開くプロジェクトを最初から読み込み（空のプロジェクトを作ってから開き直さない）、フォントの一覧を 1 回だけ作り、入力デバイスの一覧を裏で調べるようにした |
| 素材の範囲より完全に前を読むと、PCM キャッシュの読み込みが例外を出していた（ゆっくりのサンプルで見つかった） | 範囲の外は無音を返すようにした |
| 録音の入力が例外を出すと、録音のスレッドごとアプリが落ちた | 例外を記録して、録音を止めたときに知らせるようにした |

### 残っている課題

- **タイムラインの描画**：測ったのは、テスト用の画面のない環境での CPU 描画です。実際の画面（Windows では GPU で合成）では速くなるはずですが、まだ測っていません。
  時間の半分以上は文字の描画なので、遅いときは、名前を描くアイテムを減らす（短いアイテムは描かない）などを検討します。
- **10 分の書き出し**：実時間の 1.99 倍で、目標の 2 倍にわずかに届いていません。時間の多くはエフェクトとトランジションの CPU 描画なので、M2 の GPU 描画で改善する見込みです。
- **最初の起動**：PC を起動して最初の 1 回は 3.9 秒かかります（ファイルの読み込みとコンパイル）。配布するときは ReadyToRun でコンパイルしておきます（`PublishReadyToRun`）。
- **Linux・macOS**：CI でのビルドとテスト（CLI での書き出しを含む）は用意しましたが、手元に環境がないため、まだ動かしていません。

## 2026-11-05（M1 の残り：未達の 2 項目）

環境は D-16 と同じです（Let's note SV1、電源につないだ状態）。I-39 で届かなかった 2 つを直して、測り直しました。

| 目標 | I-39 | 今回 | 判定 |
| --- | --- | --- | --- |
| 10 分の動画の書き出し（QSV）：実時間の 2 倍速 | 301.7 秒（1.99 倍） | h264_qsv で 243.3 秒（2.47 倍） | 達成 |
| アイテム 3,000 個のタイムライン：スクロール 60fps | 1 回 19〜25ms | 画面のない環境の CPU 描画で、1 回 10〜12ms | 達成 |

| 問題 | 対策 |
| --- | --- |
| 書き出しが、長い動画ほど遅くなっていた（2 分で 2.46 倍、5 分で 2.33 倍、10 分で 1.99 倍）。フレームごとの評価で、レイヤーのすべてのアイテムを並べ直し、トランジションのたびにレイヤーを調べ直していた | シーンごとに 1 回だけ作る索引（`SceneIndex`）で、そのフレームに関わるアイテムだけを二分探索で取り出すようにした。2 分・5 分とも 2.56 倍、10 分で 2.47 倍になり、長さで遅くならなくなった |
| タイムラインの描画の 6 割以上が、アイテム名の文字の配置（スクロールで新しい名前が見えるたびに `FormattedText` を作る）と描画だった | アイテム名は、文字ごとのグリフと幅を覚えておき、グリフを並べて描くようにした（`GlyphLabels`。グリフのない文字はほかのフォントに切り替える）。塗りのブラシも使い回し、名前が収まるアイテムでは切り抜かない |

あわせて、I-39 の「Linux・macOS」の課題も片付けました。macOS 用の FFmpeg（LGPL・OpenH264・kvazaar 付き）をソースからビルドするようにし、CI の Ubuntu と macOS（arm64）で、CLI での書き出しを含むテストが通ることを確かめました。

## 2026-11-07（M2 A-2：GPU の事前調査）

基準の PC（Let's note SV1、Iris Xe、ドライバー 32.0.101.7080）で、M2 の GPU 描画の前提を確かめました。
vulkaninfo と、コミットしない使い捨てのプログラム（Vortice.Vulkan 3.3.0、SkiaSharp 3.119.4）で調べています。

| 項目 | 結果 |
| --- | --- |
| Vulkan の版 | 1.4.323（ローダーは 1.4.313） |
| RGBA16F（`R16G16B16A16_SFLOAT`） | 読み書き（storage）・サンプリング・描画先・ブレンド・線形の補間のすべてに対応 |
| 機能 | タイムラインセマフォ、synchronization2、dynamic rendering、`VK_EXT_memory_budget`、`VK_KHR_external_memory_win32`、shaderFloat16 |
| Vulkan Video | `VK_KHR_video_decode_h264`・`h265`・`av1` に対応。デコード専用のキューファミリー（キュー 2 つ）がある |
| キュー | グラフィックス・コンピュート・転送のキューファミリーは 1 つで、キューも 1 つ |
| Skia（SkiaSharp）で自前のデバイスを使う | `GRContext.CreateVulkan` に自前の VkInstance・VkDevice・VkQueue を渡して動いた。自前で作った RGBA16F の VkImage を `GRBackendTexture` で包んで描け、読み戻しも正しい |
| 速さ | デバイスの作成 98ms。320×120 の文字の描画と完了待ち 0.28ms |

計画への反映：

- **コピーしないデコード**：基準の PC は Vulkan Video に対応しているので、第 1 段（Vulkan Video を同じデバイスで使う）で進めます。F-32（D3D11 から取り込む）は作りません。
- **キュー**：グラフィックスのキューは 1 つしかないので、計画どおり Skia と自前のシェーダーで 1 つのキューを共有し、GPU のスレッドを 1 本にします。FFmpeg のデコードは、デコード専用のキューファミリーを使います。
- **Skia**：Windows の SkiaSharp は Vulkan に対応していて、自前のデバイスと FP16 の画像で使えます（macOS は計画どおり、CPU で描いて送ります）。

## 2026-11-07（M2 D-20：エフェクトとトランジションも GPU で描くようにしたあと）

基準の PC（Let's note SV1、Iris Xe）で、`nmm bench --renderer cpu` と `--renderer vulkan` を比べました（動画なし、60 枚ずつ、4 スレッド）。
GPU 版は続けて 2 回測り、温度による揺れが大きかったので、両方を載せています（左が 1 回目）。

| 場面 | スレッド | CPU 版（fps） | GPU 版（fps） |
| --- | ---: | ---: | ---: |
| フル解像度・8 レイヤー | 1 | 47.1 | 95.3・110.9 |
| フル解像度・8 レイヤー | 4 | 141.4 | 147.9・182.4 |
| 1/2 解像度・8 レイヤー | 1 | 137.2 | 283.0・304.0 |
| 1/2 解像度・8 レイヤー | 4 | 311.1 | 594.3・623.8 |
| 1/2 解像度・3 レイヤーにぼかしと色調補正 | 1 | 107.5 | 251.4・188.9 |
| 1/2 解像度・3 レイヤーにぼかしと色調補正 | 4 | 422.1 | 479.1・510.6 |
| フル解像度・3 レイヤーにぼかしと色調補正 | 1 | 44.6 | 60.9・71.8 |
| フル解像度・3 レイヤーにぼかしと色調補正 | 4 | 133.3 | 128.3・179.3 |

- 1 スレッドでは、GPU 版は CPU 版のおよそ 2 倍の速さです。4 スレッドでも、ほぼ同じか速くなります。そのため、自動（`--renderer auto`・アプリの既定）では GPU を使うようにしました。
- フル解像度の 1 枚（8 レイヤー）の内訳は、GPU の処理が 3〜6ms、結果（8MB）を読み戻して写すのが 2〜4ms でした。読み戻しは、表示を GPU のまま行う（I-40）か、書き出しで NV12 にしてから読む（G-34）ことで減らせます。
- 回転する文字など、毎フレーム変わる文字と図形は、まだ CPU で描いてから GPU に送っています（C-13 の方式）。

## 2026-11-07（M2 F-29：動画を YUV の平面のまま GPU で RGB にする）

- GPU 版は、動画のフレームを YUV の平面（NV12・P010）のまま受け取り、シェーダーで RGB にします（swscale を使わない）。
- 基準の PC で、1080p の NV12 を 1 枚送って RGB にし、出力に重ねて読み戻すまでが 11.0ms でした（読み戻しの 8MB を含む）。
- CPU で同じ平面を RGB にしたもの（YuvConversion）と、GPU の結果の差は 51.8〜52.2dB です（違いは、回した縁のアンチエイリアス）。

## 2026-11-07（M2 G-34：書き出しで GPU が NV12 を作る）

- GPU 版の書き出しは、作業用の画像から GPU で直接 NV12（BT.709・リミテッドレンジ、色差の位置は左）を作って読み戻し、そのままエンコーダーに渡します（BGRA にも swscale にも通しません。読み戻す量は 1080p で 8MB から 3MB）。
- `nmm bench --project samples/general/general.nmmproj --only export --repeat 6`（1 分、h264_qsv）：

| 描画 | 時間 | 実時間の |
| --- | ---: | ---: |
| GPU（NV12） | 21.2 秒 | 2.84 倍 |
| CPU（BGRA → swscale） | 37.6 秒 | 1.60 倍 |

- M2 の目標（3 倍以上）まで、あと少しです。調整は J-41 で行います。

## 2026-11-07（M2 I-40：プレビューの表示のためのコピー）

プレビューは、描いた結果（GPU 版では読み戻した BGRA）を、毎フレーム WriteableBitmap に写して表示しています。
1080p60 で間に合うかを、基準の PC（Let's note SV1、Iris Xe）で測りました（`PreviewCopyPerformanceTests` が測った値を出力します）。

| 測ったもの | 1 枚の時間 |
| --- | ---: |
| 1080p の BGRA を WriteableBitmap に写す | 1.0〜1.1ms |
| 1080p の 1 枚を GPU で描き、読み戻して写すまで（1 枚ずつ順に、動く図形が 1 つ） | 7.5〜7.8ms |

- `nmm bench --project samples/general/general.nmmproj --only playback`（30fps・10 秒）：フル解像度で表示 268・飛ばした 2（0.7%）、1/2 解像度で表示 257・飛ばした 7（2.7%）でした。
- 写すのにかかる時間は 60fps の 1 フレーム（16.7ms）の 1 割に満たず、描いて読み戻すまでを含めても半分ほどです。
  再生では 3 枚を並べて描くので、表示のためのコピーは間に合っています。
  そのため、計画の「間に合わなければ入れる」としていた Avalonia の GPU 連携（D3D11 の共有テクスチャ）は、今は入れません。
- Avalonia が WriteableBitmap を画面に出すときの転送（描画のスレッドで行う）は、ここでは測れていません。
  J-41 で、1080p60 の動画を含む場面を再生して、飛ばしたフレームの割合で確かめます。
