# 描画の設計（GPU 版）

M2 で入れた GPU 版の描画（`src/NakkuntMovieMaker.Rendering.Vulkan`）の要点です。CPU 版（`SkiaCpuBackend`）は「正しい結果」を出す基準として残し、GPU 版はそれと比べて確かめます。

## 流れ

1. 呼び出したスレッドで、ノードを GPU の処理にする（`VulkanBackend.Prepare`）。
   - エフェクトのない画像・動画：素材の画素をそのまま GPU に送り、合成のシェーダー（`composite.slang`）で重ねる。
   - エフェクトのあるノード：中身を CPU 版と同じ細かさの画像にし、エフェクトは GPU でかける（`GpuEffects`）。静止したものは、エフェクトをかけた結果を GPU に覚えておく。
   - トランジション：前後のアイテムを、それぞれ出力と同じ大きさの透明な作業用の画像に描いてから、GPU で混ぜる（`GpuTransitions`）。
   - エフェクトのない文字・図形：GPU のスレッドで、Skia の GPU 版（同じデバイスとキュー）で、描かれる範囲だけ描く（K-3）。
   - それ以外（立ち絵など）：描かれる範囲だけ CPU で描いて送る。
2. GPU のスレッド（`GpuScheduler`、1 本）で、作業用の画像に順に重ね、BGRA にして読み戻す。

## 作業用の画像

- premultiplied の RGBA を、16 ビット浮動小数点で持ちます。
- どの GPU（MoltenVK・lavapipe を含む）でも動くように、画像ではなくバッファーに入れます（1 画素 8 バイト）。
- 16 ビット浮動小数点への変換は整数の演算だけで行い、SPIR-V の Float16・Int16 の機能は使いません（`SpirvTests` で確かめています）。

## CPU 版と合わせていること

- ぼかしは、Skia の CPU 版と同じく、3 回の箱型のぼかし（SVG の feGaussianBlur の方法）です。箱の幅は `floor(σ·3·√(2π)/4 + 0.5)` で、1 以下ならぼかしません。
- 縁取りの距離変換は、CPU 版と同じ方法（Felzenszwalb と Huttenlocher）を、列ごと・行ごとに GPU で行います。
- モザイクのブロックの分け方は、CPU で表にしてから GPU に渡します。
- 不透明度は、Skia と同じく 1/255 の単位に丸めます。

## 比べるときの基準

`ParityTests` は、ゴールデン画像の 28 の場面を、同じプロセスで CPU 版と GPU 版で描いて比べます。
GPU 版は 16 ビット浮動小数点で計算し、途中で 8 ビットに丸めないので、少しだけ違います。

| 場面 | 基準（PSNR） | 基準の PC での結果 |
| --- | ---: | ---: |
| 合成・色のエフェクト・モザイク・シャープ | 45dB 以上 | 51.1〜∞ |
| 文字・図形（Skia の GPU 版で描く） | 38dB 以上 | 45.7〜67.2 |
| 縁取り | 42dB 以上 | 71.7 |
| ぼかし・影・発光・マスク・振動 | 38dB 以上 | 46.0〜69.0 |
| トランジション | 42dB 以上 | 51.8〜∞ |

調べるときは、`NMM_PARITY_DUMP` にフォルダーを指定すると、両方の画像を PNG で書き出します。

## 方式の選び方

- 自動（既定）では GPU を試します。ソフトウェアの Vulkan しかないとき、自己テスト（`GpuSelfTest`）に通らないとき、前回 GPU の準備の途中で止まったとき（目印のファイル）は、CPU で描きます。
- 描いている途中で GPU が使えなくなったら、CPU に切り替えます（`FallbackBackend`）。
- `nmm` の `--renderer`（`auto`・`cpu`・`vulkan`）で選べます。環境変数 `NMM_VULKAN_DISABLE=1` で GPU を使わないようにできます。

## 色（M2 の手順 E）

- **合成の色空間**（プロジェクトの設定）
  - 既定は sRGB です（M1 と同じ見た目）。
  - リニアにすると、作業用の画像をリニアの Rec.709 にし、重ねる・混ぜる・トランジションをリニアで計算します。黒から白への 50% のクロスフェードは、sRGB で 128、リニアで 188 になります。
  - 素材・文字・図形の色と、エフェクトの中の計算（色の処理・ぼかし）は、どちらのモードでも sRGB のままです。
- **OpenColorIO**（`NakkuntMovieMaker.ColorManagement`、ネイティブは `nmm_ocio`）
  - 構成は OCIO に組み込まれた ACES の構成を、版付きの名前で使います（既定は OCIO の既定の構成）。
  - 変換は `BakedColorLut` で、シェーパー（√x を等間隔に並べた 4096 の表）と 65³ の 3D LUT に焼いて、CPU と GPU で同じように引きます。格子に出力をそのまま入れたものと、リニアに戻して入れたもの（引いたあとで sRGB の伝達関数をかける）を作り、誤差の小さいほうを使います。
  - SDR の変換は、OCIO そのものとの差が 2/1023 以内です。PQ のトーンマップ（ACES 2.0 の HDR 1000 nits → SDR）は、色域の境界の近くで急に曲がるので、99% の色で 27/1023 以内です。
- **変換をかける場所**

| 場所 | 設定 | 処理 |
| --- | --- | --- |
| 入力 | 素材ごとの入力の色空間（`Asset.ColorSpace`） | 素材を読んだときに、作業用の sRGB にする（HDR はトーンマップ）。CPU で変換してから描画に渡す |
| 表示 | 利用者ごとの設定（`AppSettings.PreviewColorSpace`） | プレビューの描き終えた画像にかける |
| 出力 | プロジェクトの設定（`ExportColorSpace`） | 書き出す画像にかける |

- どれも、指定がなければ変換しません（OpenColorIO がなくても、M1 と同じに描けます）。
- 表示と出力の変換は、CPU 版は描き終えた 8 ビットの画像に、GPU 版は読み戻す前（16 ビット浮動小数点のまま）にかけます。GPU 版と CPU 版の差は 51dB 以上です（`output/*` の場面）。

## 動画の受け取り方（M2 の手順 F）

GPU 版は、動画のフレームを次の順に試して受け取ります（素材ごとに、できなかった方式は次から試しません）。使っている方式は `ProjectMediaSource.VideoDecodeMethod` でわかります。

| 順番 | 方式 | 中身 |
| --- | --- | --- |
| 1 | Vulkan Video（試験的） | FFmpeg に描画と同じ Vulkan のデバイスでデコードさせ、フレーム（VkImage）を GPU の上でバッファーに写して RGB にする。メインメモリを通らない |
| 2 | D3D11 からの取り込み（Windows） | d3d11va でデコードした 1 枚を、D3D11 の中で共有のテクスチャ（NT ハンドル）に写し、Vulkan に取り込んで（VK_KHR_external_memory_win32）平面ごとにバッファーに写す。メインメモリを通らない。H.264 は既定では使わない |
| 3 | YUV の平面 | NV12・P010 のままメインメモリに写して GPU に送り、GPU で RGB にする（swscale を使わない）。H.264 はソフトウェアで、ほかの形式はハードウェア（d3d11va など）を先に試してデコードする |
| 4 | BGRA | 4:2:0 でない動画（4:2:2・4:4:4・RGB・透明あり）は、これまでどおり swscale で BGRA にする |

- **Vulkan Video は、既定では使いません**（`RendererOptions.ExperimentalVulkanVideo`、または環境変数 `NMM_VULKAN_VIDEO=1` で使えます）。
  - FFmpeg 9.0.2 と基準の PC（Iris Xe）のドライバーでは、デコードの途中でプロセスごと落ちることがあります。`samples/general` の `clip.mp4` は、2 つ目のキーフレームで必ず落ちます。テスト用の動画でも、4 回に 1 回ほど落ちます。
  - FFmpeg の `ffmpeg` コマンド（`-hwaccel vulkan`）でも同じように落ちるので、FFmpeg かドライバーの不具合です。
  - 落ちないときは、写して送る方式と同じ絵になります（差はありません）。検証レイヤーのエラーもありません。
  - そのため、Vulkan Video のテストは `NMM_TEST_VULKAN_VIDEO=1` のときだけ回します。
- **FFmpeg とキューを共有する**
  - グラフィックスのキューは描画と FFmpeg で共有するので、送る前に同じ錠（`VulkanDevice.QueueLock`）を取ります。
  - デコードしたフレームは、FFmpeg のセマフォを待ってから読み、読み終わったら値を 1 つ進めて合図します。
- **FFmpeg の Vulkan の構造体**（`AVVulkanDeviceContext`・`AVVkFrame`）は FFmpeg.AutoGen にないので、ヘッダーをコンパイルして確かめたオフセットで読み書きします。FFmpeg が自分で作ったデバイスを、同じオフセットで読んで確かめるテストもあります。
- **H.264 はソフトウェアでデコードする**（J-41）。ハードウェア（d3d11va）でデコードすると、メインメモリへの写しが描画と同じ GPU を待つため、
  1080p60 で 1 枚 6〜10ms・4K で 22ms かかり、ソフトウェア（2〜4ms・4K で 8ms）より遅くなりました。動画を含む描画は、3 スレッドで 44fps から 109fps になりました。

## 書き出し（M2 の手順 G）

- GPU 版の書き出しは、作業用の画像から GPU で直接 NV12（BT.709・リミテッドレンジ）を作って読み戻し、そのままエンコーダーに渡します（`to_nv12.slang`）。
  BGRA にも swscale にも通さないので、読み戻す量は 1080p で 8MB から 3MB になります。
- 色差は左の位置に合わせ、横は 1:2:1 のフィルター、縦は 2 行の平均で作ります。
- 出力の色の変換（書き出しの色空間）は、NV12 にする前に、16 ビット浮動小数点のままかけます。
- GPU が出力と同じ大きさで描くときだけ、この方式を使います。それ以外（CPU 版、大きさを変えて書き出すとき）は、これまでどおり BGRA を swscale で変換します。

## プロキシ（M2 の手順 H）

- プロキシは、H.264・短い GOP・B フレームなしで、大きさは 1/2（最大 1080p）です。元のタイムスタンプと色のタグを写します（`ProxyGenerator`。`nmm proxy` でも作れます）。
- 作ったプロキシは、プロジェクトの `.nmm/cache/proxies` に置きます。
- **プレビューだけで使い、書き出しでは必ず元の素材を読みます**（`ProjectMediaSource` にプロキシの仕事（`ProxyQueue`）を渡すのはプレビューだけ）。
  プロキシを読むときも、素材の大きさは元のまま扱うので、配置や拡大率は変わりません。
- プロジェクトの設定（使わない・1080p より大きい動画だけ・すべての動画）に合う動画は、プロキシがなければ後ろで作り始め、できるまでは元の素材を読みます。
  作ってあるプロキシは、設定に合わない大きさの動画でも使います（使わない、にしたときと、プレビューで切ったときを除く）。削除したプロキシは、自動では作り直しません。

## 画面（M2 の手順 I）

| 場所 | 中身 |
| --- | --- |
| 設定の「描画」 | 描画の方式（自動・GPU・CPU）、使う GPU、GPU のメモリの上限、Vulkan Video（試験的）、プレビューの表示の色空間、今の描画の方式と、使えなかった理由 |
| 状態バーの右 | 今の描画の方式。望んだ方式を使えずに CPU で描いているときは警告の色にし、理由をツールチップに出す |
| プロジェクトの設定 | 合成の色空間、OpenColorIO の構成、書き出しの色空間、プロキシを使う範囲 |
| 素材の一覧 | 入力の色空間とプロキシの状態（右クリックで指定する・作る・削除する）。変換できないとき・プロキシを作れないときは、理由を出す |
| 「表示」のメニュー | プレビューでプロキシを使う |

- 描画の方式・GPU・メモリの上限・Vulkan Video は、次にプロジェクトを開いたときから使います。プレビューの表示の色空間は、OK を押すとすぐにかかります。
- プレビューは、描いた結果（GPU 版では読み戻した BGRA）を毎フレーム WriteableBitmap に写して表示します。1080p で 1 枚約 1ms なので、Avalonia の GPU 連携は入れていません（[performance.md](performance.md) の I-40）。

## D3D11 からの取り込み（M2 の手順 K-2）

- FFmpeg 9.0.2 の d3d11va は、デコードした画像を 1 つのテクスチャ配列に入れます（配列の大きさは、覚えておくフレームの分）。配列をデバイスの間で共有するのは対応が不安定なので、
  1 枚ずつ、こちらが作った共有のテクスチャ（`SHARED | SHARED_NTHANDLE`、配列ではない）に `CopySubresourceRegion` で写します（`D3D11VideoDevice.CopyFrame`）。
- 写し終わりは D3D11 のイベントのクエリーで待ち（デコードのスレッドで）、そのあと描画の GPU が読みます。FFmpeg も同じ D3D11 の文脈を使うので、FFmpeg の錠を取ってから使います。
- 共有のテクスチャは、大きさと形式ごとに 32 枚まで作って使い回します。フレームを捨てるまで、そのテクスチャはほかのフレームに使いません。足りないときは、メインメモリに写す流れに戻ります。
- Vulkan には、テクスチャごとに 1 回だけ取り込みます（`FfmpegD3D11Device.Import`。専用の割り当て）。描くたびに、外部のキューファミリーから受け取り（`GENERAL` → `TRANSFER_SRC`）、2 つの平面をバッファーに写して、外部に返します。
- D3D11・DXGI の COM は、要る関数だけを関数表の番号で呼びます（`D3D11Interop`）。依存するパッケージは増やしていません。
- 描画と同じ GPU（アダプターの LUID が同じ）でデコードします。`NMM_D3D11_IMPORT=0` で使わないようにできます。

## 文字と図形を Skia の GPU 版で描く（M2 の手順 K-3）

- エフェクトのない文字と図形は、GPU のスレッドで、Skia の GPU 版（`GRContext.CreateVulkan`。描画と同じインスタンス・デバイス・キュー）で描きます（`SkiaGpu`）。
  描く先は、こちらが作った RGBA16F の画像（大きさを 64 画素単位にそろえて使い回す）を、Skia の面にしたものです。描く処理は CPU 版と同じもの（`SkiaCpuBackend.DrawRegion`）を使います。
- 描いた画像は、作業用の形式（16 ビット浮動小数点）のバッファーに写して重ねます（作業用の画像と同じ並びなので、そのまま写せます）。リニアのモードでは、Skia がリニアで描きます。
- SkiaSharp では、Skia が描き終えた画像のレイアウトを読めないので、`COLOR_ATTACHMENT_OPTIMAL` として扱い、写したら戻します。テストで、検証レイヤーのエラーがないことを確かめています。
- Skia は自分でキューに送るので、送るときは `QueueLock` を取ります。Skia の描画は、そのフレームの描画の仕事より先に送るので、同じキューの上で順番が守られます。
- 動かないものは、描いた結果を覚えておきます（キーには色のモードも入れます）。
- 自己テスト（`GpuSelfTest`）で、図形を CPU 版と比べて 38dB に届かなければ、文字と図形は CPU で描いて送ります。macOS と、環境変数 `NMM_SKIA_GPU=0` のときも使いません。
- 立ち絵は、これまでどおり CPU で描いて送ります。動かない立ち絵は描いた結果を覚えていて、送るのも 1 回なので、GPU で描くには、パーツの画像を GPU の画像として覚えておく仕組みが別に要ります。

## macOS（MoltenVK）で動かすときの注意（M2 の手順 K-1）

- MoltenVK は SPIR-V を Metal のシェーダーの言語（MSL）に変換してからコンパイルします。変数などの名前が MSL の予約語（`device`・`constant`・`thread` など）だと、
  変換したシェーダーをコンパイルできず、パイプラインを作れません（`composite` の変数 `device` で、CI の macOS のすべての GPU のテストがスキップになっていました）。
  `SpirvTests.AvoidsNamesReservedInMetal` で、シェーダーの名前に予約語がないことを確かめます。
- 調べるときは、環境変数 `MVK_CONFIG_LOG_LEVEL=2` を付けて `nmm probe --gpu` を実行すると、MoltenVK のエラー（Metal のコンパイルの失敗の理由）と、自己テストの結果が出ます（CI の macOS でも実行しています）。
- CI の macOS（仮想の GPU）でも、GPU のテストを必ず回します（`NMM_REQUIRE_VULKAN=1`）。文字と図形は、macOS では CPU で描いて送ります（SkiaSharp の macOS 版は Vulkan に対応していない）。
